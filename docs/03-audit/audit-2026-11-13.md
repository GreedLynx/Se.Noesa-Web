- **Tanggal audit:** 13 November 2026

- **Metode:** audit statis kode + pemeriksaan konfigurasi + uji non-destruktif lokal (PHP lint, unit test UI, probe HTTP header/endpoint)

## 1. Ringkasan Eksekutif

Secara umum fondasi aplikasi sudah baik: **seluruh query memakai prepared statement**, password memakai `password_hash()`/bcrypt, upload divalidasi dengan `getimagesize()` dan nama file acak, kuota harian dikunci secara atomik, dan transisi status pesanan memakai `UPDATE ... WHERE status = ...` sehingga aman dari race condition.

Namun aplikasi **belum siap produksi** karena tiga hal mendasar:

1. **Tidak ada proteksi CSRF sama sekali**, sementara cookie sesi tidak memakai `HttpOnly`, `SameSite`, maupun `Secure`. Satu halaman berbahaya dapat memicu aksi tulis atas nama admin/owner yang sedang login.
2. **Bukti pembayaran dan foto kiriman dapat diakses publik tanpa autentikasi**, padahal berisi data perbankan dan alamat pelanggan.
3. **Kredensial demo (`owner123`, `pelanggan123`) ikut tertanam di `database/schema.sql`** dan terdokumentasi. Jika file itu dipakai untuk produksi, akun owner langsung bisa diambil alih.

Selain itu ada satu **bug fungsional yang membuat fitur tidak berjalan**: halaman kelola metode pembayaran mengirim `POST`, tetapi API-nya hanya menerima `GET` sehingga selalu `405`.

| Tingkat | Jumlah | Tema utama |
|---|---:|---|
| **Kritis** | 3 | CSRF/sesi, upload publik, kredensial default |
| **Tinggi** | 9 | brute force, XSS, debug endpoint, kebocoran error, otorisasi, header, tipe JSON, timezone, kuota upload |
| **Sedang** | 14 | validasi, performa, audit log, drift dokumen/skema, fitur rusak, aksesibilitas, CI |
| **Rendah** | 3 | skema mati, aset tak terpakai, observabilitas |

#### K1 — Tidak ada CSRF protection, cookie sesi tidak dikeraskan

**Bukti**

```php
// app/bootstrap.php:2
session_start();
```

- Tidak ditemukan satu pun kemunculan `csrf`, `xsrf`, atau token anti-forgery di `public/` maupun `app/`.
- `session_start()` dipanggil tanpa `session_set_cookie_params()`, sehingga default PHP menghasilkan cookie `PHPSESSID` tanpa `HttpOnly`, `SameSite`, dan `Secure`.
- Semua aksi tulis memakai `POST` dengan sesi cookie: validasi/tolak pesanan, ubah produk, ubah kuota, buat pesanan offline, checkout, unggah bukti, dan pembatalan.
- Contoh endpoint yang terpengaruh: `public/admin/api/orders.php`, `public/admin/api/products.php`, `public/admin/api/schedules.php`, `public/pelanggan/api/orders.php`, `public/owner/api/*`.

**Dampak**

- **CSRF:** situs penyerang dapat memancing admin/owner yang sedang login untuk mengubah produk, memvalidasi pembayaran palsu, atau membuat pesanan. Tanpa `SameSite`, browser tetap mengirim cookie pada request lintas situs.
- **Pencurian sesi:** tanpa `HttpOnly`, XSS (lihat T2) dapat membaca cookie sesi; tanpa `Secure`, cookie dapat terkirim lewat HTTP.
- **Session fixation:** sudah dimitigasi sebagian oleh `session_regenerate_id(true)` saat login (`public/api/auth.php:30`) — ini nilai positif.

**Rekomendasi**

1. Set parameter cookie sebelum `session_start()` di `app/bootstrap.php`:

```php
session_set_cookie_params([
    'lifetime' => 0,
    'path'     => '/',
    'httponly' => true,
    'secure'   => isset($_SERVER['HTTPS']),
    'samesite' => 'Strict', // atau 'Lax' bila ada alur redirect eksternal
]);
session_start();
```

2. Tambahkan token CSRF per sesi dan verifikasi di semua request non-`GET`:

```php
// bootstrap
if (empty($_SESSION['csrf'])) $_SESSION['csrf'] = bin2hex(random_bytes(32));

// helper verify_csrf() dipanggil di awal setiap handler POST/PUT/DELETE
```

3. Kirim token ke klien lewat meta tag dan sertakan pada header `X-CSRF-Token` di helper `api()` pada JS. Tolak dengan `419` bila tidak cocok.
4. Sebagai lapisan tambahan, terapkan `SameSite=Strict` dan validasi header `Origin`/`Referer` untuk endpoint mutasi.

**Prioritas:** P0 — blocker go-live.

#### K2 — Bukti pembayaran dan foto kiriman dapat diakses publik

**Bukti**

- `public/admin/api/orders.php:49` menyimpan foto ke `public/uploads/dispatch/`.
- `public/pelanggan/api/orders.php` menyimpan bukti transfer ke `public/uploads/payments/`.
- Folder `public/uploads/{payments,dispatch,products,payment-methods}` tidak memiliki proteksi; file dapat diminta langsung lewat URL.
- Uji lokal: `GET /uploads/payments/<file>.png` → **HTTP 200 tanpa login**.

**Dampak**

- Bukti transfer umumnya memuat **nama rekening, nomor rekening, nominal, dan nama bank** → kebocoran data pribadi/keuangan.
- Foto kiriman dapat memuat **wajah, rumah, dan alamat pelanggan**.
- Nama file memang acak (`bin2hex(random_bytes(...))`), jadi tidak mudah ditebak, tetapi URL tetap dapat bocor lewat riwayat browser, tangkapan layar, log server, atau referrer. Ini bukan kontrol akses.
- Produk dan metode pembayaran memang wajar publik; yang bermasalah hanya `payments/` dan `dispatch/`.

**Rekomendasi**

1. Pindahkan `payments/` dan `dispatch/` ke luar document root (mis. `storage/uploads/`) dan sajikan lewat endpoint ber-otorisasi:

```php
// public/api/file.php?type=payment&id=123
require_role(...);            // pastikan pemilik pesanan / admin / owner
// validasi path kanonik, lalu readfile() dengan Content-Type yang aman
```

2. Jika ingin tetap di `public/`, blokir langsung di web server:

```apache
# public/uploads/.htaccess
Require all denied
```

lalu tetap sediakan endpoint pengganti. Jangan hanya mengandalkan `.htaccess` bila server bisa berganti ke nginx.
3. Tambahkan `Content-Disposition: inline` + `X-Content-Type-Options: nosniff` pada endpoint file.
4. Audit file lama: file yatim akibat order gagal harus dibersihkan (lihat T9).

**Prioritas:** P0 — blocker go-live.

#### T1 — Brute force login & kebijakan password lemah

**Bukti**

- `public/api/auth.php:18-33` — percobaan login tidak dicatat, tidak dibatasi, dan tidak ada jeda.
- `public/api/auth.php:45-47` — registrasi hanya mewajibkan **6 karakter**.
- `public/forgot-password.php:33` — reset password justru mewajibkan 8 karakter, jadi kebijakan tidak konsisten.
- Tidak ada CAPTCHA, tidak ada lockout per akun/IP, tidak ada `sleep()`/delay.
- Pesan error login seragam (baik) tetapi tanpa throttling tetap dapat di-brute force.

**Dampak**

- Password `owner123`/`pelanggan123` dapat ditebak dalam hitungan detik.
- Credential stuffing terhadap akun pelanggan nyata.
- Beban CPU dari `password_verify` berulang (bcrypt) dapat dijadikan vektor DoS ringan.

**Rekomendasi**

1. Terapkan rate limit per IP + per akun (mis. 5 percobaan / 15 menit, lalu jeda eksponensial). Simpan hitungan di tabel `login_attempts` atau Redis.
2. Naikkan minimum password ke 10–12 karakter, tolak password umum, dan samakan aturan dengan alur reset.
3. Tambahkan `password_needs_rehash()` saat login untuk migrasi hash lama.
4. Catat login sukses/gagal ke audit log (lihat S3).
5. Pertimbangkan CAPTCHA setelah 3 kegagalan.

**Prioritas:** P0/P1.

#### T2 — Stored XSS di dashboard owner

**Bukti**

```js
// public/assets/js/app.js:410
`...<div><b>${t.nama}</b>...`

// public/assets/js/app.js:748-753
const img = p.gambar ? `<img src="../${p.gambar}" alt="${p.nama}" ...>` : ...
return `<div class="pr" ...><span class="kode">${p.kode}</span><div><b>${p.nama}</b>...`;
```

- `t.nama`, `p.nama`, `p.kode`, dan `p.gambar` disisipkan langsung ke `innerHTML` tanpa `esc()`.
- Sebagai perbandingan, `public/pelanggan/assets/customer.js` sudah konsisten memakai `esc()` — jadi pola yang benar sudah ada.

**Dampak**

- Nama/kode produk berasal dari input admin. Jika akun admin disusupi (atau ada fitur impor/seed), payload `<img src=x onerror=...>` akan berjalan di sesi **owner** dan dapat mencuri cookie (diperparah oleh K1) atau memicu aksi tulis.
- XSS di panel admin/owner jauh lebih berbahaya daripada di sisi pelanggan karena hak aksesnya luas.

**Rekomendasi**

1. Escape seluruh nilai dinamis: `${esc(p.nama)}`, `${esc(p.kode)}`, `${esc(p.gambar)}`, `${esc(t.nama)}`.
2. Validasi `p.gambar` dengan allowlist path (mis. hanya `assets/img/produk/...` dan `uploads/products/...`), seperti yang sudah dilakukan `payments.js:8`.
3. Terapkan CSP yang melarang `unsafe-inline` (lihat T6) sebagai pertahanan berlapis.
4. Audit ulang semua `innerHTML` di `public/assets/js/app.js` dan `public/admin/assets/admin.js`; cari interpolasi `${...}` yang tidak dibungkus `esc()`/`Number()`.

**Prioritas:** P1.

#### T6 — Security header tidak ada, versi PHP terbuka

**Bukti (hasil probe server lokal)**

```
Set-Cookie: PHPSESSID=...; path=/
X-Powered-By: PHP/8.5.10
```

- Tidak ada `Content-Security-Policy`, `X-Frame-Options`/`frame-ancestors`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, maupun `Strict-Transport-Security`.
- Tidak ada `header()` terkait di kode aplikasi.

**Dampak**

- Aplikasi dapat di-embed di iframe penyerang (clickjacking) — relevan karena panel admin punya aksi satu klik.
- Tidak ada CSP → XSS (T2) lebih mudah dieksploitasi.
- MIME sniffing dapat membuat file upload diperlakukan sebagai HTML/JS.
- `X-Powered-By` memudahkan pemetaan versi.

**Rekomendasi**

1. Set header global di `app/bootstrap.php` (atau web server):

```php
header('X-Content-Type-Options: nosniff');
header('X-Frame-Options: DENY');
header('Referrer-Policy: strict-origin-when-cross-origin');
header('Permissions-Policy: geolocation=(), microphone=(), camera=()');
header("Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'");
header('Strict-Transport-Security: max-age=31536000; includeSubDomains'); // hanya di HTTPS
header_remove('X-Powered-By');
```

2. Mulai CSP dengan `report-only` untuk menemukan inline script/style, lalu naikkan ke enforcing.
3. Set `expose_php = Off` di `php.ini` produksi.

**Prioritas:** P1.

#### T7 — `JSON_NUMERIC_CHECK` merusak tipe data

**Bukti**

```php
// app/bootstrap.php:51
echo json_encode($data, JSON_NUMERIC_CHECK);
```

**Dampak**

- String yang seluruhnya angka berubah menjadi number. Contoh berisiko:
  - `kode` pesanan yang kebetulan numerik;
  - `telepon`/`phone` → kehilangan leading zero dan format;
  - `nama_pemesan` yang berupa angka;
  - `id` yang dikirim sebagai string lalu dianggap number oleh klien.
- Kontrak API menjadi tidak stabil dan bergantung pada isi data, bukan pada tipe yang dideklarasikan.
- Sulit dideteksi karena baru muncul pada data tertentu.

**Rekomendasi**

- Hapus `JSON_NUMERIC_CHECK`; cast eksplisit di sisi server untuk field yang memang angka (`(int)`, `(float)`).
- Pastikan kolom uang dikirim sebagai integer (rupiah) dan tanggal sebagai string ISO.
- Tambahkan test kontrak JSON untuk endpoint utama.

**Prioritas:** P1.

#### T8 — Bug batas hari WIB pada dashboard

**Bukti**

```php
// public/admin/api/dashboard.php:6
$today = (new DateTimeImmutable('today'))->format('Y-m-d');

// public/owner/api/dashboard.php:7
$endDate = new DateTime('today');
```

- `new DateTime('today')` memakai timezone default server. PHP CLI lokal terdeteksi UTC, sedangkan logika kuota aplikasi memakai `Asia/Jakarta`.
- Query membandingkan `created_at::date` (timestamp kolom) dengan tanggal hasil PHP.

**Dampak**

- Antara 00:00–07:00 WIB, "hari ini" di server masih tanggal kemarin → pesanan hari ini tidak masuk laporan, pesanan kemarin ikut terhitung.
- Laporan owner/admin dan angka KPI bisa salah setiap pagi.
- `created_at::date` juga bergantung pada timezone sesi database; jika DB UTC, hasilnya makin bergeser.

**Rekomendasi**

1. Set `date_default_timezone_set('Asia/Jakarta')` di bootstrap **dan** `timezone = Asia/Jakarta` di `php.ini`.
2. Gunakan ekspresi SQL yang eksplisit:

```sql
(created_at AT TIME ZONE 'Asia/Jakarta')::date = ?
```

3. Terapkan pola yang sudah dipakai `pelanggan/api/orders.php:24-25` (`clock_timestamp() AT TIME ZONE 'Asia/Jakarta'`).
4. Tambahkan test untuk kasus di sekitar tengah malam WIB.

**Prioritas:** P1 (salah data, bukan sekadar kosmetik).

#### T9 — Upload tanpa batas jumlah dan tanpa pembersihan

**Bukti**

- `public/admin/api/orders.php:25-47` memvalidasi **setiap** file (maks 2 MB per file, MIME JPG/PNG/WebP) tetapi tidak membatasi **jumlah** file per request/pesanan.
- `public/admin/api/orders.php:70-74` menyimpan semua file ke `uploads/dispatch/` dan menulis baris DB per file.
- Jika `$savedPaths` kosong, `$savedPaths[0]` pada baris 74/85 dapat memicu error (lihat catatan di bawah).
- Tidak ada mekanisme hapus file saat pesanan dihapus/dibatalkan/ditolak.
- Tidak ada kuota total disk maupun pemantauan.

**Dampak**

- Satu request dapat mengunggah puluhan/ratusan file 2 MB → disk penuh, biaya storage naik.
- File yatim menumpuk dan tetap dapat diakses publik (K2).
- `post_max_size`/`upload_max_filesize` yang salah dapat menghasilkan request kosong yang membingungkan (sebagian sudah ditangani di `products.php`).

**Rekomendasi**

1. Batasi jumlah foto per pesanan (mis. maks 5) dan validasi juga di server, bukan hanya atribut `multiple`.
2. Batasi total ukuran per request.
3. Simpan metadata file (ukuran, MIME, hash) dan jadwalkan pembersihan file yatim > 30 hari.
4. Cek `empty($savedPaths)` sebelum mengakses indeks 0, meskipun secara alur saat ini tidak mungkin terjadi.
5. Pertimbangkan object storage + signed URL untuk produksi.

**Prioritas:** P1.

#### S1 — Validasi registrasi lemah
- Password 6 karakter (`auth.php:45`), tanpa maksimum, tanpa cek password umum.
- Email tidak di-`strtolower`/`trim` sebelum disimpan → login bisa gagal bila beda kapitalisasi (PostgreSQL case-sensitive).
- `username`/`phone` tanpa batas panjang/format; hanya dicek `empty()`.
- Pesan "Username atau email sudah dipakai" membocorkan keberadaan akun (enumerasi ringan) — dapat dibiarkan, tetapi sadari implikasinya.
- Tidak ada verifikasi email saat registrasi.

**Rekomendasi:** normalisasi (`mb_strtolower(trim(...))`), batas panjang eksplisit, validasi nomor telepon Indonesia, password minimal 10 + cek daftar password umum, dan rate limit registrasi.

#### S2 — Paginasi & N+1
- `admin/api/orders.php:219-224` mengambil seluruh pesanan tanpa `LIMIT`/`OFFSET`; `COUNT` terpisah di baris 226 menambah round-trip.
- Riwayat pelanggan membatasi 50 pesanan, tetapi setiap pesanan memicu query item tambahan di dalam loop (`pelanggan/api/orders.php:316-325`) → hingga 51 query per permintaan.
- **Dampak:** makin lambat seiring data; memori dan payload membengkak; rentan DoS.
- **Rekomendasi:** paginasi server-side (default 20–50), ambil item dengan satu query `WHERE pesanan_id = ANY(?)` atau `json_agg`, dan tambahkan index pada `pesanan(status, created_at)` serta `detail_pesanan(pesanan_id)`.

#### S3 — Audit log
- Tidak ada catatan siapa mengubah status, memvalidasi pembayaran, atau mengubah kuota.
- **Rekomendasi:** tabel `audit_log(actor_id, action, entity, entity_id, before, after, ip, created_at)` dan tulis di dalam transaksi yang sama.

#### S4 — Drift dokumentasi
- `docs/01-spesifikasi/api.md:82` dan `README.md:106` menyebut owner read-only, tetapi kode memberi akses tulis (T5).
- `docs/01-spesifikasi/api.md` juga menyebut pembersihan otomatis saat katalog/riwayat dibuka, sedangkan `README.md:114-115` menyatakan pembatalan hanya lewat scheduler.
- **Rekomendasi:** jadikan dokumentasi bagian dari definition of done; tambahkan test yang memverifikasi klaim kritis (role matrix, cleanup).

#### S5 — Skema tidak konsisten
- `database/schema.sql` tidak memuat `kuota_harian`, `metode_pembayaran`, view, dan beberapa kolom yang dibuat migrasi.
- Dua file memakai prefix sama: `016_multiple_dispatch_photos.sql` dan `016_order_cancellation.sql` → urutan eksekusi tidak deterministik.
- **Rekomendasi:** satukan baseline skema terbaru, beri prefix unik/berurutan, dan sediakan skrip `migrate.php` yang mencatat migrasi yang sudah dijalankan.

#### S6 — `data-dummy.sql` rusak
- Baris terakhir `</content>` adalah artefak copy-paste; eksekusi SQL akan gagal.
- **Rekomendasi:** hapus baris tersebut dan validasi file seed di CI.

#### S7 — Reset password demo hardcoded
- `scripts/reset-demo-customer-password.php` menetapkan `pelanggan123`.
- **Rekomendasi:** hapus dari repo produksi atau lindungi dengan `APP_ENV=local` + konfirmasi interaktif.

#### S8 — Fitur metode pembayaran rusak
- UI (`public/owner/payments.php`) dan `payments.js` mengirim `POST` untuk save/toggle/delete (`payments.js:37,60,105`).
- API hanya menangani `GET` dan mengembalikan `405` untuk metode lain (`owner/api/payments.php:5-12`).
- Tidak ada tautan navigasi ke halaman ini.
- **Dampak:** fitur yang diklaim berfungsi tidak dapat dipakai; pengguna bingung.
- **Rekomendasi:** implementasikan handler POST (validasi MIME/ukuran, CSRF, audit log) atau sembunyikan halaman sampai siap.

#### S9 — Tidak ada konfigurasi server/CI
- Tidak ada `.htaccess`, `web.config`, atau contoh nginx; tidak ada workflow CI; tidak ada test PHP otomatis (hanya 3 skrip Node UI).
- **Rekomendasi:** simpan konfigurasi referensi di `deploy/`, jalankan `php -l`, test Node, dan (idealnya) PHPUnit di CI.

#### S10 — Field jadwal tidak ditegakkan
- `jadwal_po` memiliki `tgl_buka`, `tgl_tutup`, dan `kapasitas`, tetapi checkout hanya memilih jadwal aktif pertama (`pelanggan/api/orders.php:222`) tanpa memeriksa tanggal/kapasitas.
- `docs/01-spesifikasi/aturan-bisnis.md:33` menyatakan `jadwal_po` hanya referensi — jadi ini bisa disengaja, tetapi UI admin tetap menampilkan field yang tampak mengikat.
- **Rekomendasi:** jika memang referensi, beri label jelas di UI; jika ingin ditegakkan, validasi tanggal window dan kapasitas di checkout.

#### S11 — Aksesibilitas
- Form login/registrasi memakai `<label>` yang membungkus input tanpa teks label; satu-satunya nama aksesibel adalah `placeholder` (`login.php:20-33`, `register.php:12-46`). Placeholder hilang saat mengetik dan tidak selalu dibacakan screen reader.
- `confirm()` native untuk pembatalan (`customer.js:530`) tidak dapat didesain/dibacakan konsisten dan memblokir thread.
- Render ulang `innerHTML` (mis. `app.js:748`, `customer.js:167`) menghilangkan fokus keyboard; tidak ada manajemen fokus setelah update.
- `dialog` sudah dipakai dan beberapa tombol punya `aria-label` — nilai positif.
- **Rekomendasi:** label visual + `for`/`id`, ganti `confirm()` dengan `<dialog>` yang ada, kelola fokus (`focus()` ke heading/error), dan uji dengan keyboard + screen reader.

#### S12 — `body()` menelan JSON invalid
- `json_decode(...) ?: $_POST` membuat JSON rusak/kosong dianggap `[]`, lalu validasi menghasilkan pesan "kolom wajib diisi" yang menyesatkan.
- **Rekomendasi:** bedakan `json_last_error()` dan kembalikan `400 Bad Request` dengan pesan jelas.

#### S13 — Fitur notifikasi setengah jadi
- API/UI Admin, Owner, dan pelanggan sudah tersedia. Migrasi 022 menambahkan
  audit persetujuan dan tindak lanjut manual.
- **Sisa verifikasi:** uji integrasi alur pelanggan→persetujuan Admin, selisih
  harga, akses kepemilikan, dan tampilan detail pesanan sebelum rilis.

#### S14 — `nama_pemesan` diisi nama penerima
- Checkout mengirim `$recipient` ke kolom `nama_pemesan` (`orders.php:244-246`), sehingga laporan "nama pemesan" menampilkan nama penerima.
- **Rekomendasi:** tambahkan field `nama_pemesan` terpisah di checkout, atau rename kolom menjadi `nama_penerima` agar makna konsisten.

## 3. Hal Positif (Pertahankan)

1. **SQL injection:** semua query memakai `prepare()` + parameter terikat melalui helper `q()` (`app/bootstrap.php:38-45`). Tidak ditemukan interpolasi input pengguna ke SQL, kecuali `$statusFilter` yang berasal dari allowlist switch (`admin/api/orders.php:210-216`) — pola yang benar.
2. **Password:** `password_hash(..., PASSWORD_DEFAULT)` dan `password_verify()` (`public/api/auth.php:27,56`); tidak ada MD5/SHA1.
3. **Session fixation:** `session_regenerate_id(true)` saat login (`auth.php:30`).
4. **OTP:** kedaluwarsa 10 menit, maksimal 5 percobaan, resend 60 detik, hash OTP, dan pesan netral "jika email terdaftar" — implementasi yang matang.
5. **Upload:** validasi MIME via `getimagesize()`, allowlist ekstensi, ukuran maks 2 MB, nama file acak, dan pembersihan file saat transaksi gagal (`admin/api/orders.php:37-43,56,76-82`).
6. **Kuota:** `LOCK TABLE` + `SELECT ... FOR UPDATE` + validasi dalam satu transaksi (`pelanggan/api/orders.php:210-231`) — kuat terhadap oversell.
7. **Transisi status:** `UPDATE ... WHERE status = ...` mencegah race condition dan double-processing.
8. **Escape di sisi pelanggan:** `customer.js` konsisten memakai `esc()` dan `Number()`; ini contoh yang harus diikuti `app.js`.
9. **Struktur:** pemisahan `app/`, `config/`, `public/{owner,admin,pelanggan}`, API per domain, dan dokumentasi `docs/` sudah rapi dan mudah dinavigasi.
10. **Test UI:** tiga skrip Node berjalan dan lulus (lihat bagian 4).
